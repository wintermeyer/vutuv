## vutuv visual design system — "Direction A"

Every page must use this one visual language. It is "confident professional-bold":
deep heritage **blue** + a **coral** accent, white cards on a light grey canvas,
clean typography. **Dark mode follows the system** (`prefers-color-scheme`) — there
is **no theme toggle**, and every surface/text needs `dark:` variants.

### Two page styles — know which one you're touching

Every page is styled one of two ways: a **classic page** (legacy controller +
`.html.heex` view page, styled by the shared classes in `assets/css/components.css`)
or a **kit page** (hand-written markup built from the `VutuvWeb.UI` component kit +
Tailwind recipes). This is a *styling* distinction, not a module category — a
LiveView can sit on either style.

1. **Classic pages** (legacy controller+view pages) still use shared classes (`.card` / `.card-list`,
   `.editform` + inputs (`.editform__hint` is the muted helper line under a field, e.g.
   "Markdown is supported"; its `--ok` brand-blue / `--error` red variants color the live
   username-availability verdict that app.js writes under the new-username field),
   `.button` + variants, `.breadcrumbs`, `.profile-header` page
   title, `.pure-table`, `.alert`, `.tags`/`.badges`, `.imagebox`,
   `.profiles` (+ the `.profiles--tags` variant whose rows grow to fit a
   `.profile-tags` line: up to 4 small tag links plus a `.profile-tags__more`
   "+N more tags" overflow count, used by the most-followed listing via
   `card_list`; `card_list` also takes an optional `filed_names` assign that
   swaps each row's link text for `UserHelpers.filed_name/1` ("Özil, Mesut") —
   only the member directory's letter pages pass it, because they are the one
   listing sorted by last name, and a natural-order column under a heading of
   "M" makes the reader hunt for the word the order is built on),
   `ol.tags`/`.upvote`, `ul.thumbs` (flex rows: capped
   thumbnail + truncating URL), `.reorder*` (the member's drag-and-drop ordering
   tool shared by every orderable section page — links, phone numbers, addresses,
   social media accounts, emails — and by the ranked language list on
   `/settings/feed_languages`, where the "rows" are codes in an array column
   rather than records with a `position`: `.reorder__item` draggable tile =
   `.reorder__handle` grip + `.reorder__body` (section-specific, with a
   `.reorder__thumb` for links) + `.reorder__move` up/down `.reorder__btn` arrows
   (sized as touch targets) + `<.row_actions>`. It is **not** a classic page: on the
   section pages it is the embedded `VutuvWeb.SectionReorderLive` (`live_render`,
   owner-only, like the shell) and on the language page a plain routed
   `VutuvWeb.FeedLanguagesLive`, so both drag and arrows persist over the socket with no reload — the
   `Reorder` hook in `app.js` does the drag, the arrows are `phx-click`. The hook
   also FLIP-animates the arrow reorders (snapshot row tops in `beforeUpdate`,
   glide them from old to new spot in `updated`, ~180ms; honors
   prefers-reduced-motion). Mobile-first: touch can't fire native drag, so the
   arrows are the reorder path on phones), `.card__tablewrap` (every in-card `<table>`
   sits in this overflow-x scroller so a wide table scrolls instead of being
   clipped by the card's `overflow:hidden` — `card_table_scroll_test.exs`
   enforces it), `tr[data-row-changed]` (the **live-row marker**: a table row that
   changed while the member was only looking at the page sweeps once through a
   brand tint and back to transparent, 1.4s — for a table whose rows can move
   without anybody here touching them, like `/settings/fediverse/following`,
   where the answer to a follow comes from another server. The tint is the
   custom property `--row-changed-tint`, which is why light/dark share one set
   of keyframes and why the `prefers-reduced-motion` rule can paint the very
   colour it would otherwise have faded — under reduced motion the row is still
   pointed out, it just stands still. **The marker must be put on by the server
   on exactly the rows that moved and taken off again** after the sweep, or the
   table lights up on every page load and a row that changes twice lights up
   once: a CSS animation restarts only when the element begins matching the rule
   afresh),
   `.breakwrap` (break a long unbroken string and cap the line at a
   readable measure — use it instead of an inline `word-wrap`/`max-width` style),
   `.card__empty` empty-state line, `.card__label` (the small uppercase muted
   caption for field/section labels inside a legacy card — e.g. the detail show
   pages and the tag card; it is `<h2 class="card__label">` so each page keeps
   exactly one `<h1>` while the prominent `.card h2` styling stays available),
   `.error-page` 404/403/500
   card). They
   are styled **centrally** in `assets/css/components.css` — since the old vendored
   `legacy.css` was removed, that file is the **single source** for these classes,
   including element defaults (body canvas, h1/p/a, label, tables, dl) and the data-URI
   icons. **To restyle legacy pages, edit `components.css` — do NOT reskin
   per-template.** A new legacy page that reuses these classes gets the look for free.
   **Dark mode for all of it lives in the `@media (prefers-color-scheme: dark)` block
   at the end of `components.css`** — when you add a light rule with a hardcoded
   colour, add its dark counterpart there. `test/vutuv_web/dark_mode_css_test.exs`
   guards the canvas rule and that `legacy.css` stays deleted.
2. **Kit pages** (new / hand-written: the shell `ShellLive`, the LiveViews,
   `user/show.html.heex`, the logged-out auth/welcome pages via `<.auth_layout>`)
   use the **`VutuvWeb.UI` components** (see **Components** below) or, where no component
   fits, the **recipes** below. Prefer a component; fall back to a recipe. Reach for a
   green-field rewrite only when a page's UX needs rethinking (like the profile) —
   otherwise keep it a classic page.

### Tokens (defined in `assets/css/app.css` `@theme`)

- **Brand blue:** `bg-brand-600` (primary), hover `bg-brand-700`; text `text-brand-700` / `text-brand-800`; tint `bg-brand-50`. The scale is **sparse** — only these steps exist in `@theme`: `50, 100, 200, 300, 400, 500, 600, 700, 800, 900` (**no `950`**). `brand-300` (`#93c5fd`, the natural light-blue step used for dark-mode link/hover text) was added once ~14 files relied on it and it was silently compiling to nothing; `brand-950` still doesn't exist, so a `brand-950` class silently compiles to nothing — pick a defined step. After adding/changing utility classes in a `.ex`/`.heex`, rebuild (`mix tailwind vutuv`) and confirm each shipped by grepping `priv/static/assets/app.css` for the **escaped** selector (variants escape `:` to `\:`, e.g. `grep -F 'dark\:hover\:bg-brand-900'`).
- **Accent (unread counts / CTAs highlight):** `bg-accent` / `text-accent` (coral `#f97362`).
- **Surfaces:** page is grey (`slate-50`/`slate-100`); cards `bg-white`; borders `ring-slate-200`; text `text-slate-900 / 700 / 500`. **Muted/secondary text is `text-slate-600 dark:text-slate-400`** — passes WCAG AA on both white cards and the slate canvas. **Don't use bare `text-slate-400` as a text colour**: it fails AA (~2.6:1 on white) and is gone from the templates; `slate-400` now lives on only as the `dark:` half of the muted pair. Even `slate-500` is borderline directly on the slate-100 canvas (breadcrumbs, footer), so those use `slate-600`. A WCAG axe-core sweep keeps the key pages clean.
- **Dark:** `dark:bg-slate-900` (cards) / `slate-950` (page), `dark:ring-slate-800`, `dark:text-slate-100 / 300 / 400`. `app.css` sets `html { color-scheme: light dark }` and `root.html.heex` ships a `theme-color` meta per scheme (`#ffffff` / `#020617`).

### Canonical recipes (copy these exactly)

- **Page root:** `<main>` already gives `mx-auto max-w-6xl px-4`. A page's own wrapper is e.g. `py-6` (+ `grid gap-6 md:grid-cols-3` for a content+rail layout — `md`, not `lg`, so portrait iPads get the columns too). Don't add another `max-w`/`px` unless intentional. **Give the main content column `min-w-0`** (e.g. `min-w-0 space-y-4 md:col-span-2`): Tailwind's `md:grid-cols-*` compiles to safe `minmax(0,1fr)` tracks, but only at `md+`; below `md` (every phone) the grid falls back to an implicit `auto` track that respects the item's min-content, so a single `truncate`/unbreakable descendant (a threaded reply's parent-excerpt, a markdown body) forces the column — and the whole page — wider than the viewport and scrolls it sideways. `min-w-0` lets the column shrink below that min-content. `mobile_overflow_test.exs` guards the feed / profile / dev-doc columns.
- **Card:** `rounded-2xl bg-white p-6 shadow-sm ring-1 ring-slate-200 dark:bg-slate-900 dark:ring-slate-800` — or `<.card>`.
- **Section title:** `text-sm font-semibold uppercase tracking-wide text-slate-500 dark:text-slate-400` — or `<.section_title>`. The `dark:` half is required, like every other muted text: bare `slate-500` on a dark card is ~3.8:1, under AA, and 14px semibold is not large text.
- **Primary button:** `rounded-lg bg-brand-600 px-4 py-2 text-sm font-semibold text-white hover:bg-brand-700`.
- **Secondary button:** `rounded-lg bg-slate-100 px-4 py-2 text-sm font-semibold text-slate-700 hover:bg-slate-200 dark:bg-slate-800 dark:text-slate-200 dark:hover:bg-slate-700`. The `dark:hover:` is required: without it the dark `slate-800` flips to the light `slate-200` on hover.
- **Text link / "Add" action:** `text-sm font-semibold text-brand-600 hover:text-brand-700 dark:text-brand-400 dark:hover:text-brand-300` — the dark pair is part of the recipe, not optional (83 call sites once shipped without it and lost contrast in dark mode); `brand_link_dark_mode_test.exs` fails the build when the light half appears without the dark half. **And `hover:text-brand-700` needs a dark counterpart wherever it appears, not only inside this recipe** — `brand-700` is `#1e40af`, about 2.3:1 on the dark canvas, so a slate link that merely turns brand on hover got *harder* to read in dark mode; 39 call sites shipped that way. Any light step (`dark:hover:text-brand-100/200/300/400`) satisfies it, and the same test's second case enforces it.
- **Input / select / textarea:** `w-full rounded-lg border border-slate-300 bg-white px-3 py-2 text-sm focus:border-brand-500 focus:outline-none focus:ring-3 focus:ring-brand-500/40 dark:border-slate-700 dark:bg-slate-800 dark:text-slate-100`. **The `focus:ring-3` is not optional and must never be dropped**: `focus:outline-none` kills the browser's own indicator, and for a while nothing replaced it, so keyboard focus on ~40 kit forms was a 1px slate→brand border change you could barely see in light mode and essentially not at all in dark (WCAG 2.4.7). The classic `.editform` controls carry the **same** two-part treatment (brand border + 3px `rgb(59 130 246 / 0.4)` halo) in `components.css`, so focus reads identically on a classic and a kit form. That classic rule is written as `.editform input[type]:focus` / `.editform input:not([type]):focus` (0,2,1) on purpose: a plain `.editform input:focus` loses the border-colour to the same-specificity, later-emitted dark-mode block at the end of the file, which is exactly how the dark-mode focus border silently stopped working. This exact string is `VutuvWeb.UI.input_class/0` (imported everywhere) — call it in HEEx as `class={input_class()}` (compose with utilities via `class={[input_class(), "resize-y"]}`) on green-field forms (the post composer, the auth pages) instead of re-typing it. **On a field that can fail validation, call `input_class(form, field)` instead**: same recipe, but once the field carries an error the slate border swaps for red (`border-red-400 focus:border-red-500 dark:border-red-500/70`), keeping the `<.form_error>` banner's "fields marked in red" true on kit pages (classic editform pages get the marking from `.editform__field--error`). Pair it with `"aria-invalid": f.errors[:field] && "true"` on the input and `error_tag f, :field` below it; when the field also has a muted hint line, render the hint only while there is **no** error (`:if={!f.errors[:field]}`) so one clear line speaks, not a stack (the sign-up tags field is the canonical example). A hand-built form with no changeset (the admin preference forms) uses `input_class(invalid?)` with a bare boolean — same two strings.
- **Checkbox (consent/opt-in box):** `mt-0.5 h-4 w-4 rounded border-slate-300 text-brand-600 focus:ring-2 focus:ring-brand-500 focus:ring-offset-2 dark:border-slate-600 dark:bg-slate-800 dark:focus:ring-offset-slate-900` — the string is `VutuvWeb.UI.checkbox_class/0` (the companion to `input_class/0`); used by the sign-up form's consent checkboxes (email visibility, search engines, AI agents). Call it instead of re-typing.
- **Tag chip:** `inline-flex items-center gap-2 rounded-lg bg-brand-50 px-3 py-1.5 text-sm font-medium text-brand-700 dark:bg-brand-900/40 dark:text-brand-100` — or `<.chip>`.
- **Unread count badge:** small `rounded-full bg-accent px-1 text-[11px] font-bold text-white`; add `ring-2 ring-white dark:ring-slate-900` when it overlaps an icon or avatar.
- **Action-bar state derived from `aria-pressed`:** `[data-count-steps]` / `[data-fills-when-pressed]` (a `components.css` block, no colours so no dark copy). Both post action bars paint a press on the spot with LiveView's JS commands, and every command is aimed at the **button**, never at a child; the glyph's fill and which of the two pre-rendered count steps shows are worked out from the button's own `aria-pressed` here. That is a correctness rule: a command aimed at a child leaves LiveView's never-expiring stash on that child, so when a refused act re-keys the button to hand morphdom a fresh node, morphdom **moves the old unkeyed children into it** and they arrive still carrying the paint (measured: a grey button around a still-filled heart). One element holds the client state, everything else reads it. `display` has exactly one owner — the count steps carry no `hidden` utility of their own (the #880 trap); `invisible` on a zero step is a different property and stays a class.
- **A press the control cannot answer by itself:** `[data-awaits-server]` (a `components.css` block, light + dark). Both action bars paint their new state on press through LiveView's DOM-patch-aware JS commands, so almost nothing needs this. The exception is a like or a reshare on a card from another network pressed by a member whose own Fediverse standing already refuses it (`Vutuv.Fediverse.outbound_standing/1` — participation is opt-in and most readers have not switched it on): painting a heart for them would be a lie, so the bar waits for the server and explains itself instead, which on a slow line is exactly the dead control the optimistic flip exists to kill. Marking such a control `data-awaits-server` makes its glyph **breathe in brand tint while LiveView's own `phx-click-loading` is on it** — deliberately not a spinner (nothing is loading, an answer is being waited for) and not a dimming (that reads as disabled). Under `prefers-reduced-motion` it holds the tint still, the same trade `tr[data-row-changed]` makes. Put it on a control that pushes an event and **cannot** show its own outcome; never on one that already paints.
- **Avatar:** `Vutuv.Avatar.display_url(user, :medium|:thumb)` in an `<img>`, `rounded-2xl` (tile) or `rounded-full` (list) + `object-cover`.
- **Link preview card** (profile Links section, main column): `grid gap-4 sm:grid-cols-2 sm:gap-x-18` (the `sm:gap-x-18` 72px desktop column gutter lines the two thumbnail columns up edge-for-edge with the Followers/Following cards below, whose content channel is `gap-6` + two `p-6` = 72px; row/mobile gap stays `gap-4`), each cell an `<a>` wrapping `<.link_thumb url={url} />` inside `overflow-hidden rounded-lg ring-1 ring-slate-200 dark:ring-slate-800`, then a `min-w-0` title/URL block (`truncate`). The screenshots come from `Vutuv.PageScreenshot` (headless Chromium, on link create/update); what a link with no screenshot looks like is `<.link_thumb>`'s call, not the call site's (see the component).

### Components (`VutuvWeb.UI` — imported everywhere; no explicit import needed)

`lib/vutuv_web/templates/user/show.html.heex` is the canonical example of the kit.

- `<.card class="…">…</.card>` — the card surface.
- `<.auth_layout title=… subtitle=…>…</.auth_layout>` — the logged-out **welcome/auth shell**: a brand-gradient hero panel (`from-brand-700 to-brand-500`, soft white decorative rings, white headline + `subtitle` + optional `:hero` slot for a member-count pill) beside a `<.card>` form (the default slot), stacking to one column under `md`. A `:headline` slot replaces the default `<h1>{title}` + subtitle when a hero needs full control over its heading typography (the landing page's founder-quote + attribution block); `title` stays required as the plain-text fallback. Used by the sign-up landing (`page/index`), `/login` and the two PIN screens so the logged-out entry flow matches the app instead of the old full-bleed photo "imagebox" (now deleted). The legal pages (impressum, datenschutz) are plain `<.page_header>` + `<.card>` content (no hero).
- `<.pin_actions email={…} context={:login|:registration} />` — the two "stuck on the PIN page" escape hatches shared by both PIN-entry screens (login `session/pin_user_login` + post-registration `page/pin_new_registration`): a "Resend PIN" and a second text-link, each a CSRF POST (to `~p"/login/resend"` / `~p"/login/cancel"`). Resend re-mails the PIN for the pending cookie identity (rate limited 5/hour) **without changing which flow it belongs to**; cancel drops the identity cookie so the landing page is no longer pinned to the PIN form. Both attrs are required and both come from `VutuvWeb.ControllerHelpers.render_pin_screen/2`, which reads them off the signed cookie and assigns `@pending_email` / `@pin_flow` — the single owner of "a PIN is pending, which screen", called by all five render sites so no screen can contradict the flow it belongs to. `context` drives two things: only `:login` suggests trying another of the member's addresses (at registration they gave exactly one and have no account yet), and only `:login` labels the second control "Use a different email address", which at registration reads "Cancel registration". The hint names the pending address in semibold, so a typo one screen earlier is visible. Uses the standard text-link recipe; no new tokens.
- `<.pin_time_left expires_at={…} />` — the quiet line under the PIN field saying how much of the PIN's 30-minute life is left, and the anchor the countdown in `app.js` ticks (`[data-pin-time-left]`). Deliberately **one muted `text-xs` line and no clock face**: the window is half an hour, and a digit ticking every second beside a field somebody is reading a number into is a nag. It counts whole minutes almost all the way down and only switches to seconds inside the last one. `expires_at` is the deadline out of the signed pending-PIN cookie, assigned as `@pin_expires_at` by `render_pin_screen/2` beside `@pending_email` / `@pin_flow` — **the deadline must not be computed per render**, because "/" is pinned to the PIN screen while a PIN is in flight and a per-render deadline would hand a reloading member a fresh 30 minutes for a PIN that is quietly dying. What reaches the browser is the **remaining seconds** (`data-pin-seconds-left`), not that timestamp, so a device whose clock runs fast cannot blank a form that is still good; the JS anchors to its own `Date.now()` at load and recomputes from it each tick, so a throttled background tab is simply correct again on return. The four plural forms ride the element as `data-label-*` (the lightbox/emoji-picker arrangement — the server is the only side that knows the locale), each a **whole sentence** per form rather than a unit word the JS glues onto a number, with `{n}` as the marker (the `split_marker/2` convention; gettext only interpolates `%{…}`, so it passes through). With JS off, or on a legacy cookie carrying no deadline, the server sentence stands and simply does not tick. **The registration screen wraps both of its states in `[data-pin-countdown]`** — `[data-pin-live]` (heading, form, this line, `<.pin_actions>`) and `[data-pin-expired]`, which ships rendered but carrying the plain `hidden` attribute and **no display utility** (the issue #880 trap) plus `tabindex="-1"` so app.js can move focus onto it. At zero the JS swaps them: hiding the live half is the point, since by then the PIN cannot verify, "Resend PIN" reads its address from the same expired cookie and "Cancel registration" would send somebody with no account to the login form. The expired panel names the grace `Vutuv.Accounts.unconfirmed_registration_grace_minutes/0` computes from the sweeper's own constants (never a number typed into a translation) and offers one primary link back to `/`.
- `<.section_title>…</.section_title>` — uppercase muted heading inside a card.
- `<.link_thumb url={…} class={…} />` — the 400×264 preview tile of a profile link, and the **one** place that decides what a link looks like with no screenshot. Three states, each carrying `data-link-thumb` for tests: a stored capture renders as the thumbnail (`shot`, `Vutuv.Screenshot.url/2`); a link this installation never captures (`site`, `Vutuv.ScreenshotBlocklist` — a consent-banner or login-walled page, admin-edited at `/admin/screenshots?tab=blocklist`) renders a calm `bg-slate-50 dark:bg-slate-800` tile with the host in muted semibold, because "a screenshot has not been created yet" is a promise that never comes true there; anything else is a capture still on its way and keeps the bundled `/images/screenshot.png` placeholder (`pending`). Sizing (`aspect-[400/264] w-full`) lives in the component, so the profile Links card (kit page) and the `/:slug/links` list (classic page) render one tile — the call site only wraps it in the link and the `overflow-hidden rounded-lg ring-1` frame.
- `<.other_formats_card base_path={…} locale={…} vcard machine_formats={…} />` — the quiet rail/footer card of small chips linking to a page's `VutuvWeb.AgentDocs` siblings (Markdown / plain text / JSON / XML, plus vCard when `vcard` is set). `base_path` is the page's extension-free path, so each chip is `base_path <> ".md"` etc.; `locale` keeps a `?lang=` suffix on the agent links (the vCard skips it). `machine_formats={false}` (default true; the profile passes `not ContentPolicy.agent_docs_blocked?(@user)` — a member with **both** `noindex?` and `noai?` set) drops the md/txt/json/xml chips (those URLs 404 for such a profile, `VutuvWeb.Plug.AgentExportOptOut`) and renders a short muted note in their place; the vCard chip stays. `rss_path` (the profile passes `VutuvWeb.Feeds.user_feed_path(@user)`) appends a visible "RSS" chip for the member feed (original posts only — no replies, no reposts); like the vCard it survives `machine_formats={false}` (the feed always serves, signalling opt-outs per response) and skips `?lang=`. Eight call sites (the feed twice, the profile, the post permalink, a job posting, an organization page and its post permalink, the media kit): the **profile** aside (`base_path={"/" <> @user.username} vcard`), the **`/feed` rail** (`base_path="/feed"`, rendered twice — desktop rail + an `md:hidden` bottom copy, so pass distinct `id`s through the global `rest`), and the **post permalink** (`base_path={@formats_base}`, gated on `@show_formats?` so a restricted post — whose anonymous `.md` would 404 — shows none). No vCard except the profile.
- `<.feed_button href={…} id={…} />` — the **subscribe-by-feed pill**: the RSS glyph (`<.icon_rss>`) plus the word "RSS" in the outline pill of `<.tag_follow_button>` / `<.follow_button variant="text">`, grown to a full `min-h-10` (40px) touch target. Glyph **and** word: the arcs mean nothing to someone who does not already use feeds, and a bare "RSS" among section headings does not read as a control. It carries `type="application/rss+xml"` (a browser or reader extension knows what it gets before fetching), a translated `aria-label` + matching `title` (the bare visible "RSS" would be a second link of that exact name in a screen reader's link list, since the rail's "Other formats" chip points at the same URL; the label keeps "RSS" inside it per WCAG 2.5.3), and `data-feed-button` for tests. Two call sites: the feed half of `<.subscribe_card>`, and the **`/:slug/posts` archive** header beside "View profile" (`id="archive-feed"`) — the one page that is nothing but posts, where the pill stands alone because a page about a single feed needs no card named after subscribing. It is **not** in a Posts card header any more.

- `<.subscribe_card id={…} feed_href={…} account_offer={…} name={…}><:fediverse>…</:fediverse></.subscribe_card>` + `<.subscribe_link href={…} id={…} />` — the **Subscribe card**, the last card of the main column on a profile and on an organization page, and the quiet sign that points at it from the Posts card header. One component for both pages: a visitor arriving from Mastodon asks the same thing of a person and of a page. It **ranks** its three parts rather than listing them. First the **account offer** (`account_offer`, a logged-out viewer only, `name` for its sentence): an account here is the best way to follow somebody — the posts arrive in a feed the reader can answer in — and it is the only thing an anonymous visitor is offered on a profile at all, since the header's follow pill needs a session. Its `<.button href={~p"/"}>` goes to the landing page, which *is* the sign-up form, beside the existing "Already a member? Sign in here." link. Then a bridging line, shown only under the offer — "No vutuv account? These ways work too:" — so the rest reads as the answer for people who do not want one rather than as a ranking the reader has to infer. Then the **Fediverse half** through the `:fediverse` slot (its three bodies differ per page: `<.follow_us_from_elsewhere>`, a moved member's forwarding address, an organization owner's `<.empty_add>` invite) and the component's own **feed half** — `<.feed_button>` beside the feed's absolute URL in a `<.copy_field>`, because a reader extension takes the click while a standalone reader wants the address pasted into its own "add feed" box. `id` is the page's prefix, not a full id: the card is `<prefix>-subscribe`, the offer `<prefix>-account`, and the Fediverse half keeps `<prefix>-fediverse`, the anchor the whole card carried before it grew its other parts, so the Profiles rail card's shortcut row and `RemoteFollowController`'s error redirect still land on the address. Each part gets a `text-sm font-semibold` `<h3>`, a hairline sets one off from the one above it, and the feed's heading says "Or with an RSS reader" only when the Fediverse half sits above it ("With an RSS reader" otherwise — most profiles do not federate; after the bridging line the "Or" would dangle off a colon). A card with no part at all renders nothing, and one named predicate per page (`UserHTML.subscribe_card?/3`, the organization LiveView's `subscribe_card?/4`) drives both the card and the header sign, so the jump is never dead.

- `<.post_filter_tabs active={…} event={…} base_path={…} options={…} {rest} />` — the **filter tab bar** (issue #945, `VutuvWeb.PostComponents`), the one control for "which of these am I looking at". The dot and the quote answer different questions and are not alternatives: the dot says *that* something is over there and stays until the tab is visited, the quote says *what* and goes on its own. **On a narrow bar the other tabs fold their labels away** so the quote gets the width — measured on a 356 px bar, the difference between no room for a quote at all and about twenty characters. Folded over their **width**, never hidden: a hidden tab leaves a hole and the rest jump into it, while a width running to zero lets the remaining tab slide across. That is why every label sits in its own `.filter-tab__label` span carrying `--n` (its length, plus two characters of slack so a word of wide capitals is never clipped at rest) — a width animates, a text node does not. An empty *tab* keeps the bar, or there is no way back. **A press paints itself**, because switching a tab reloads the list and the pill would otherwise only travel with the answer — a dead control on a slow line: the pressed tab takes the pill, the one being left goes quiet in the same frame, and every `[data-filter-list]` under the same `[data-filter-scope]` dims after a short delay (so a fast answer never flashes). **The ticker quote is painted as the tab it names**, not as a control of its own: it carries that tab's `phx-value-type`, so its `phx-click-loading` lights `.filter-tab--ticking`, quiets the tab being left and dims the list exactly as pressing that tab does — and the quote itself deepens, which is the only press feedback a touch screen gets, there being no hover to have deepened it already. It was the one control in the app that answered a press with nothing at all, which is why readers went for the tab instead. All of it is CSS reading LiveView's own `phx-click-loading`, in **`app.css` outside every cascade layer** — the resting colours are utilities, and only an unlayered rule beats the utilities layer. **That paint is not this component's, it is the app's**, and the **/notifications** filter bar (`VutuvWeb.NotificationLive.Index`, a different look and `<.link patch>` rather than buttons) is the second bar wearing it — LiveView stamps the same class on a patch link it pushes for. So the three markers are spelled without "post" in them and any filter bar can take them: **`data-filter-tab`** on each tab, **`data-filter-scope`** on the element holding the tabs *and* their list (the feed's content column, `#tag-timeline`, `#profile-posts`, the notifications column — outside it the dimming silently stops), **`data-filter-list`** on what gets replaced. The timing is one knob for the whole app, `--press-pending-delay` (plus `-fade` / `-opacity`) on `:root` in `app.css` — change the feel there, never at a call site. Colour is the one thing a bar names for itself, through `--press-on-bg` / `--press-on-fg` / `--press-off-fg`: the default is the brand pill, and `data-filter-bar="track"` on the container switches to the white-pill-on-a-trough look, so a pressed tab always turns into **that bar's own** active tab. **The same paint serves both navs** — see the shell facts below. A press that lands **before** the view has joined is not lost either: `app.js` repeats it (12 × 500ms) until LiveView marks it in flight, since a `phx-click` button is bound only once its socket — the embedded child's, for the profile and the tag timeline — has joined, and until then a press reached nothing at all. A tab that is a **link** needs none of that and deliberately gets none: an archive tab is a plain navigation, and a patch link with no socket yet falls back to a full page load of the same URL, so the early press already lands.

The bars grow **leftwards from a common right baseline** — the faces are `justify-end` inside a cell padded to the full bar width (`--endorser-bar`, inline, `32px + (n-1) × 26px`), and the **`+N` value label past the bar's end sits in its own fixed `w-10` column**, so a two-digit remainder can't shove one row's bar out of line with the next. That `+N` is how many endorsers the bar leaves out (`total - faces`), a quiet muted label rather than a chip, and it adds up with the chip's count pill in the same row. The faces are real endorsers (newest first, never repeated filler) and an endorsed tag keeps **at least one** (a bar that rounded away would read as "nobody"). It shows **no sentence**: a naming line per row buried the tags in prose. That sentence ("Endorsed by NAME and N others", `ngettext` + `compact_count`) lives on as the strip's `title` / `aria-label`, so hover and assistive tech still get it and one tap reaches the page that names everyone — the reason this page exists, `<.tag_vote>`'s hover roster being a popover no touch device can open. Viewer-independent (the endorse control on that page is the chip's own count pill, not this), renders **nothing** for an honor tag or a tag nobody endorsed, and reads the same `endorsements` preload (`UserTagEndorsement.visible_with_endorser/0`), so it costs no query.
- `<.avatar_stack users={…} cap={5} size="2xs" overlap={…} total={…} />` — a row of **overlapping avatars**, each linking to that member's profile with their name as its tooltip, the rest folding into a trailing `+N` chip. The compact "these people did this" strip beside a sentence that names them, so the stack itself is `aria-hidden` decoration; the post card's "Reposted by" banner and its "Liked by" row (below) are the call sites. **`total`** says how many people the strip stands for when that is more than `users` holds, so the `+N` covers people who have no face: the permalink's likes pass the like count itself, because a member who turned attribution off is still one of the likes (issue #1233) and the tally must not shrink. Without it the overflow is simply `users` past `cap`. `overlap={false}` gives a spaced row instead of the shingled default, keeping a picture-less member's two-letter monogram fully visible. The faces come from the private `stack_faces/1`, which `<.endorsed_by>` shares (it needs the same faces but its own link, geometry and value label); each face carries `data-stack-face`, so a test counts faces instead of matching avatar markup.

- `<.local_time at={dt} id={…} style={…} format={…} class={…} />` — the **one** rendering of a non-post timestamp. Stored times are UTC, so it always emits the `datetime`/`title` as unambiguous ISO-8601 with a trailing `Z` (naive datetimes treated as UTC, `DateTime`s via their own offset), the form the `LocalTime` pass converts from — hand-rolling a space-separated stamp made some browsers read it as *local* time. **Who writes the visible text depends on the reader** (issue #1502): once a member has picked a time zone on /settings/preferences the server renders in it, the element carries no `data-localtime` and no hook, and their setting beats whatever machine they are reading on; without one (an anonymous visitor, or a member who never chose) nothing on the server knows their zone, so the `<time data-localtime>` is rewritten client-side exactly as before. `style` picks the shape from the reader's date region (`Vutuv.DateRegions`): `:datetime` (default), `:date`, `:short_date`, `:day_month`, `:time`, `:datetime_seconds`. Pass `format` instead to pin a literal `Calendar.strftime/2` pattern — what the **admin** tables do, where an ISO date is the point and a member's German or American shape would only get in the way of comparing rows; every member-facing call site uses `style`. Pass `id` inside a LiveView so the `LocalTime` hook can attach (it needs a DOM id); omit it on classic pages, where `app.js`'s `time[data-localtime]` sweep handles it. **`precision="second"`** (default `"minute"`) emits `data-localtime="second"`, which makes the client rewrite keep the **seconds** (`timeStyle: "medium"`); pair it with `style={:datetime_seconds}` so both halves agree. Minutes are right for "when did this arrive", but the account-activity log (issue #1087) is the case where they are not, since pinning a change down to the second is that page's whole point. Used by the messages thread, the tag-endorsers list, the account-activity pages and the admin ad pages — **don't hand-roll a `<time>` for a UTC stamp; render this** (or `<.post_time>` for posts). For a bare `%Date{}` — an issue date, a job's expiry, a birthday — there is no instant to shift, so call `Vutuv.ViewerClock.format(date, :date)` instead; it writes the reader's shape and never touches the zone.
- `<.post_time at={dt} id={…} class={…} />` — the **post** timestamp, rendered **server-side in the reader's own time zone and date region** (`Vutuv.ViewerClock`, issue #1502; before that every post was stamped in Europe/Berlin for everybody), with **no** client rewrite — the wording is relative to the reader's calendar day and only the server knows which day that is. A post from **today** shows just the time (German "08:42 Uhr" on a 24-hour region, a bare "8:42 AM" on a 12-hour one — the "Uhr" suffix is dropped on a 12-hour clock, since "2:30 PM Uhr" is not a thing anyone says); one from **yesterday** the word plus the time ("Gestern, 08:42 Uhr" / "Yesterday, 8:42 AM", no numeric date); older posts the short date and time in the reader's region ("02.07.26, 08:42" / "7/2/26, 8:42 AM"). Language and region are **independent axes**: the language picks the words, the region picks the digits and the clock. The `<time>` keeps a UTC `datetime` for machines/agents and a full-date `title` for hover, but the visible text is final from the server, so it deliberately carries **no** `data-localtime` marker (the JS localizer skips it). Because today/yesterday moves with each reader's own midnight, **`Vutuv.DayClock`** broadcasts `:day_changed` on the `"clock:day"` PubSub topic on **every whole UTC hour** (every IANA zone's local midnight falls on one) and the post-showing LiveViews (feed, profile, notifications) re-render their stamps then (feed/notifications re-stream the shown entries with `update_only: true`; the profile re-fetches its posts list), so an open page rolls "08:42 Uhr" over to "Gestern, 08:42 Uhr" at the reader's midnight with no reload — an open **dead** page (the post permalink) still waits for the next load. Used by the post card and the thread/notification post preview (`VutuvWeb.PostComponents`).

- **`.upload-drop*`** (a `components.css` block, not a component) — the **file drop zone** on a classic `.editform` page (the Arbeitszeugnis upload). - `<.tag_input id=… name=… value=… field_id=… placeholder=… field_class=… invalid?=… max=… />` — the shared **tag pill box**, the one field for every batch of tags: the add-tag form (`TagNewLive`), the sign-up landing page, the invitation form, the post composer and both job-posting tag fields (DRY). Only a **comma** separates two tags (`Vutuv.Tags.parse_tag_names/1`), so a multi-word tag is typed out plainly — and because a plain text box shows no seam between one tag and the next, members read the space as a separator too and created tags they never meant to. Progressive enhancement, not a widget: the component renders one ordinary `<input type="text">` holding the comma-joined value, which **is** the feature with JS off; `assets/js/tag_input.js` then switches it to `hidden` (it stays the form field, so nothing about the request changes), builds the box beside it and mirrors every change back — including the half-typed tail, so a submit mid-word keeps that word. The root is `phx-update="ignore"` — the pills are the client's — while its attributes still patch, which is how a server-driven value change reaches it: `data-value` mirrors `@value` and the hook re-seeds from it (a restored draft, the composer clearing after a post), ignoring the echo of what it sent itself. Styling is `.tag-input*` in `components.css` (light + dark), reproducing `input_class/0` down to the two-part brand focus treatment, which the box takes on `:focus-within` since the element you type in is a borderless child; pills use the `<.chip>` brand tint. `field_class` styles the no-JS input (`input_class()` on a kit page, nothing on a classic `.editform` page); pass `field_id` when a `<label for=…>` or an `error_tag/2` span points at the field — the JS moves that id onto the box the member types in. **`max` caps the pills** (issue #1237): past it the box refuses the next pill, keeps that text in the entry rather than swallowing it (silently dropping it is the very bug the cap exists to fix) and shows `.tag-input__notice` underneath — a `role="status"` line that borrows the `.editform__error` recipe, `!` glyph included, and is turned off by name (`[hidden]`) because `display: flex` would beat the browser's own rule. - `<.markdown_editor id=… name=… value=… label=… placeholder=… rows=… submit_on=… compact images />` — the shared **Milkdown WYSIWYG Markdown editor**, the one composer surface for **both** posts (`PostLive.Composer`) and direct messages (`MessageLive.Index`) — DRY. **`submit_on="cmd-enter"`** (both composers pass it, issue #1196) makes Cmd/Ctrl+Enter submit the surrounding form from the WYSIWYG surface and the source textarea — one handler in the hook, which skips the shortcut while the form's submit button is disabled (the post composer disables its button during photo uploads); the "?" shortcuts overlay lists it. **`images`** (post composer only — messages, organization and job bodies stay image-free) enables inline post images end to end: a 🖼 toolbar button that opens the form's LiveView file input, drop/paste-into-the-prose upload (the hook forwards the files to that input and remembers the drop position), at-cursor insertion once the server finishes processing (`mde-image-uploaded` / `mde-insert-image` push events from the composer), an own-upload-only image policy in the prose (`OWN_IMAGE_SRC` — a pasted remote image vanishes, mirroring the server), and per-image **alignment buttons** (`.mde__group--image`, revealed via `data-mde-img` while an image node is selected; active choice = `aria-pressed`) that store the choice as a `#left`/`#right`/`#center` fragment on the image src — no fragment = full width; `VutuvWeb.Markdown` maps fragment → `post-inline-image--*` modifier at render time and the editor CSS previews it off `img[src$="#…"]`. It is a rich-text surface over a **plain-Markdown store**: the real form field stays a hidden `<textarea name={@name}>` holding Markdown *source*, and the `MarkdownEditor` JS hook (`assets/js/markdown_editor.js`) renders/edits that source with Milkdown, mirroring it back to the textarea on every change (so `phx-change`/`phx-submit` and the server pipeline are unchanged — `VutuvWeb.Markdown` still renders the stored source and the agent-format siblings are untouched). Everyone gets WYSIWYG by default; the **"MD"** toolbar button toggles a raw-Markdown source view for power users, **"⤢"** expands to a near full-page editor, and with JS off the plain textarea shows through as the fallback. The enabled features are exactly the subset `VutuvWeb.Markdown` renders — bold, italic, strikethrough, links, bullet/ordered lists, headings, blockquote, inline + fenced code, tables, horizontal rules; **task-list checkboxes are deliberately excluded** (Earmark renders them as literal text). **Footnotes are the one feature the server renders that the editor deliberately has no node for** (issue #1147): `[^1]` and its `[^1]: note` line stay ordinary text in the WYSIWYG, which is what a member typing them expects to see, and the whole feature costs the composer two mirrored string transforms instead of a schema, a keymap and an input rule that could corrupt a body on a round trip. Those two are not optional, and both cover a **silent** remark behaviour: it escapes `[` in phrasing content (so the editor would store `\[^1]` and the renderer would stop recognizing the footnote), and it parses `[^1]: https://example.com` — the most natural footnote there is — as a CommonMark **link reference definition**, a node `@milkdown/preset-commonmark` has no schema for, so re-opening such a post would drop the line entirely. `escapeFootnotes` escapes `[^…]` on the way IN (remark then sees an escaped bracket, never a link definition, and shows the plain `[^1]` the member typed) and `canonicalizeFootnotes` unescapes on the way OUT; the backslash is never visible and never stored. `VutuvWeb.Markdown.Footnotes` reads through the escape too, as the guard for bodies stored before this existed. **Emoji** (issue #1197) come in two ways, both storing the **character**: a 🙂 toolbar button opens the picker (`assets/js/emoji_picker.js`, `.emoji-picker*` in `components.css`), and typing `:tada:` swaps itself for 🎉 on the closing colon — a ProseMirror `InputRule` in the prose (so one undo puts the shortcode back) plus its twin on the source textarea, gated to `mode === "source"` because in WYSIWYG that same `input` event is the mirror `writeSource/1` fires with the caret parked at the end of the value. An unknown name stays exactly as typed, which is what someone writing about `:hover` or a `key: value:` line expects. Shortcodes are only ever read, never written, so **no server code takes part**: no emoji table, no pipeline step, and the `.md`/`.txt`/`.json`/`.xml` siblings, RSS, mail and the fediverse all carry the emoji already. (Earmark renders no shortcodes and the GFM *spec* defines none — GitHub substitutes them in its own layer above cmark-gfm — so "Earmark does GFM" is not a route to this.) The dataset is `assets/js/emoji_data.js`: ~440 curated emoji in 8 groups, each `[character, shortcodes, english, german]`, bundled into app.js rather than fetched, so the first tap opens instantly and an air-gapped install needs nothing. Search matches **both** languages' words whatever the UI language ("Herz" and "heart" both find ❤️), by substring since German compounds need it ("blume" finds 🌻), then ranks word-start matches first so "herz" does not lead with the 😉 hiding inside "scherz". The only translated words are the group tabs, passed in as `data-emoji-groups="key:Label|…"` — all picker copy comes from `data-emoji-*` (the lightbox arrangement: the server is the only side that knows the locale), while the emoji themselves are labelled with their language-neutral `:shortcode:`, which doubles as a hint for the type-through. `markdown_editor_test.exs` fails the build if a dataset group has no label; `emoji_data_test.exs` guards the table's own invariants (a shortcode outside `[a-z0-9_+-]` could never be typed through, a duplicate alias would point at the wrong picture). The panel is appended to `<body>`, outside every LiveView root, or an unrelated re-render would patch it away. The group tabs are toggle buttons with `aria-pressed`, deliberately **not** `role="tab"` (a real tablist owes the reader a roving tabindex); the grid's buttons are `tabindex="-1"`, so the search field is the keyboard entry point — Enter takes the top match, Down/Right steps into the grid, arrows walk it, Escape closes and hands the caret back. **Mobile is its primary shape**: under 40rem it is a bottom sheet (`60dvh`, safe-area padding, 2.75rem targets, a backdrop, and a ✕ that only shows there) and it deliberately does **not** focus the search field, since the on-screen keyboard would cover the grid it is meant to help you scan; desktop gets a popover pinned under the button (flipped above when the window is short) that stays open for a second pick. `place/0` decides the sheet-vs-popover chrome on every call, not once at open time, because rotating a phone crosses 40rem.

**The phone's top toolbar row is a budgeted space, and the budget is arithmetic.** The toolbar's width is the viewport minus the page gutter (32), the card padding (48, flat `p-6` at every width), the frame border (2) and its own padding (13) — so 295px at a 390px viewport — and the row carries **eight** controls: B, I, link, emoji, photo, the chevron, then MD and full screen pushed right by `.mde__spacer`. It fits while 8 × the button size stays under that, which is why `.mde__btn` **cannot** honour the ~40px touch-target rule here (8 × 2.5rem = 320px) and steps instead: **2.25rem (36px) from 25rem up, 2rem (32px) below it**. That keeps all eight on one row from 360px, which is what Stefan asked for on 2026-07-30 after MD and full screen wrapped onto a second line. The step boundary is 25rem, not the 24rem where 36px *just* stops fitting, because "just" was one pixel of slack at 384px and a breakpoint needs room for a scrollbar or a rounding difference. A 320px viewport has 225px and wraps whatever we do (fitting it would mean 28px targets), which is the accepted floor. The same budget is why **strikethrough and inline code sit in `.mde__more-row`, not the first group** — the emoji button took their place up top, and they are the first thing the chevron reveals. `markdown_editor_test.exs` asserts that split by comparing where each `data-mde-cmd` sits relative to `mde__more-row`, so a tidy-up cannot quietly cost the phone a whole row again. Measuring this needs the box-model arithmetic above, not the browser tooling: `resize_window` is inert for the automation Chrome, so the media query cannot be flipped by resizing (to see the real thing, lift the shipped `@media (width < 40rem)` rules out of the CSSOM — recursing through the `@layer components` wrapper — re-insert them without the media wrapper, and stub `window.matchMedia` so the JS takes its phone branch). Styling is `.mde*` in `components.css` (its own ProseMirror base + Direction A prose, light + dark), **not** utilities. The editor **caps its height and scrolls** (`.mde__mount` `max-height`: 24rem for posts, 10rem for the `.mde--compact` message composer) rather than growing without bound — an uncapped editor overflowed the fixed chat panel; fullscreen removes the cap. On phones (`< 40rem`) the toolbar **collapses to one row** (inline marks + the MD / full-screen controls); a chevron `.mde__more-toggle` reveals the secondary groups (`.mde__more-row`: headings, lists, table, hr) on a wrapped row below (the `is-open` class it toggles lives on the toolbar, inside the ignore frame, so it survives re-renders). Everything shows inline on `sm+`. **Anything with an `:if` that renders ABOVE this editor needs a wrapper that is always there** (`#composer-notice` around the restored-draft notice, `#typing-slot` around the messages typing bubble): a conditional sibling that comes and goes makes morphdom relocate the form below it, re-parenting the editor's `contenteditable` blurs it, and LiveView restores focus for `<input>`/`<textarea>` only — so the caret is thrown out mid-sentence and the following keystrokes are lost (the "jumping cursor"; see the LiveView rule in `.claude/rules/phoenix.md`). Two more gotchas the hook already handles, keep them if you touch it: (1) the editor's view state (ready/mode/fullscreen) lives in **JS**, re-stamped in `updated/0`, because morphdom strips JS-set attributes off the server-managed root on every keystroke — and the same is true of the height the member **drags the source textarea to** (`resize: vertical` writes it onto that element's inline `style`, and the textarea is the server-rendered form field), so `beforeUpdate/0` copies it and `applyState/0` puts it back, or the box springs to its default height on the next keystroke or paste (issue #1143); (2) **the server SAYS when the editor should take `@value` again, with `data-mde-seed`; the rendered value is never a command by itself.** `data-mde-value` seeds the editor at mount, and after that the prose belongs to the writer: the composer echoes the body back on every keystroke, so a patch of this editor is the normal case, and `replaceAll`-ing the document on one moves the caret to the end and drops whatever was typed since that render was built. Bump the seed where the editor must let go — `reset_composer/1` (posting, "Discard draft") and the message page's `assign_form/1` (after a send) — and nowhere else; a form that is only ever seeded at mount (the organization and job-posting descriptions) passes no seed at all. The old rule was "re-seed whenever the value differs from what I last pushed", which reads a **late** echo as a command: with two changes in flight the patch answering the older one lands while the editor already holds the newer text, so the prose snapped back a character and the caret jumped to the end, then did it again milliseconds later when the newer answer arrived (measured over a simulated 1.5s link; it is the second, non-morphdom half of the "jumping cursor"). The hook still repairs the **hidden textarea** on such an echo — morphdom overwrites that field because nothing focuses it in WYSIWYG mode, and `save` submits what it holds — by writing the editor's text back silently, with no `input` event. Milkdown emits a literal `<br />` for an empty paragraph **or an empty table cell**, which the renderer would escape to literal text; the hook normalizes those out at write time (`normalizeMarkdown`) and `VutuvWeb.Markdown.strip_break_artifacts/1` strips them at render time (fence-aware) as the guard for already-stored bodies. Milkdown likewise serializes **URLs** in remark's two forms — a recognized link as an autolink `<https://…>`, a bare URL as escaped literal text `https\://…\&…` — but vutuv stores **bare, unescaped** URLs and autolinks them server-side, so `normalizeMarkdown` (`canonicalizeUrls`) drops the autolink brackets and the backslash-escapes at write time; the server carries **no** render-time URL repair (issue #918 — a leftover `\.` used to break Earmark's link parser and leave a stray `)`), and a one-off migration (`RepairMilkdownEscapedUrls`) cleaned the bodies stored before the fix. It likewise escapes the **underscore in a `@handle`/`#hashtag`** (`@ulrich_wolf` → `@ulrich\_wolf`, `_` being a Markdown emphasis char) — Earmark undoes it before the renderer links the mention, so a post *renders* fine, but `Vutuv.Mentions` reads the raw source and the stray backslash truncated `@ulrich\_wolf` to the non-existent `@ulrich`, which made the mention-existence check reject a real member; so `normalizeMarkdown` (`canonicalizeMentions`) strips the escape **inside a mention run only** (a literal `\_foo\_` in prose keeps its escapes), `Vutuv.Mentions` also sees through the escape on the source side (`unescape_handle_chars/1`), and `RepairMilkdownEscapedMentions` cleaned the bodies stored before the fix. The third of the same family is a **`user@host` address** — a fediverse handle `@php@tags.vutuv.de` or a plain email — which GFM's autolink literal parses into a `mailto:` link node, so remark writes it back either as an autolink `<php@tags.vutuv.de>` (after any re-parse: draft restore, post edit) or, on a first write, as escaped text `php\@tags.vutuv.de`. The first shipped and was reported: `<` is escaped at render time, so the member's sentence read `@<php@tags.vutuv.de>` on the page. The second is the one to fear, because it is not cosmetic — that backslash splits **one fediverse handle into the two local handles** `@php` and `@tags`, so the mention-existence check refuses to save the body at all. `normalizeMarkdown` (`canonicalizeAddresses`) undoes both and `RepairMilkdownEscapedAddresses` backfilled the stored bodies. **The pattern is the point: any Markdown syntax remark knows and vutuv does not store is a round-trip hazard, and each one costs an editor transform plus a repair migration.** When you touch this editor, ask what remark does to a construct vutuv keeps as plain text — and measure it (a few lines of node against the pinned remark), because all four of these were invisible in every test. **And the other direction: Earmark does not read every valid spelling under every option.** CommonMark writes a hard break two ways, a trailing backslash or two trailing spaces, and Earmark takes the backslash only while `breaks: false` — with `breaks: true` its `<br>` rule matches bare whitespace before the newline instead, so remark's perfectly correct `\` fell through as literal text and stood at the end of every hard-broken line in a chat message, a tagline, an organization description and a job posting (v7.308.1; `normalize_hard_breaks/1` now respells it before Earmark, which repairs the stored bodies too and is why this one needed no migration). So check an editor output under **both** `breaks:` values, not only the one the post body uses — `render_post/3` was clean throughout, which is exactly what made the bug look like it belonged to messages. Post bodies add a `markdown--post` modifier (post card + the profile post list) that flattens **all headings to plain bold body text** (`font-size: 1em`) — big H1/H2 made short posts noisy; dev docs and legal pages keep the heading hierarchy. `.markdown--post` also **hyphenates** the post body (`hyphens` + the `-webkit-hyphens` prefix iOS/Safari needs, keyed off the document `lang` de/en) so long German compound words (Digitalisierung, unternehmenseigene) wrap at syllable points instead of leaving ragged gaps in the narrow column; `code`/`pre` opt back out (`hyphens: manual`) so technical tokens keep their exact characters at every width. Hyphenation is now a **per-reader, per-breakpoint preference** (language & display settings, `User.post_prefs/1`): the post body sets `--post-hyphens-desktop`/`--post-hyphens-mobile` inline (via `@body_style`), and the CSS fallbacks — off on desktop, on for the narrow phone column (`@media (width < 48rem)`) — reproduce the previous fixed behaviour and also govern every OTHER `.markdown--post` (the work-experience / education descriptions), which carry no inline override. The nine `.hl-*` hues are the one deliberate exception to "stay on brand / accent / slate" — distinguishing a comment from a string from a keyword *is* the feature — and each clears WCAG AA on `#f1f5f9` (light) and `#1e293b` (dark). A fence with **no** language, or one of the "no language" words (`text`, `plain`, `none`, `txt`), renders as the plain `.markdown pre` and is left completely untouched; an unknown language still gets its label, just no colours. A long path **wraps** rather than truncating (on a phone the last segments are the ones that matter). ### Shell & layout facts (don't re-implement)

- The chrome — sticky top bar + mobile bottom tab bar with the live unread badges — is `VutuvWeb.ShellLive`, embedded in `app.html.heex`. Pages render **inside** it; never add their own nav.
- **The phone tab bar is opaque, and nothing on the page may give a `position: fixed` element a translucent, blurred layer to composite.** The top bar is frosted (`bg-white/90 backdrop-blur`) and the bottom tab bar deliberately is not (`bg-white dark:bg-slate-900`): a `backdrop-filter` has to be re-rasterized against the scrolling content on every frame, and that is the path iOS 26 Safari gets wrong on a fixed element — the bar stops following the viewport mid-scroll and hangs in the middle of the screen with the feed running on underneath it (reported on an iPhone, 2026-08-14; the frosted bars of the sites in Apple's own bug reports are the tell). The sticky top bar keeps its blur because a sticky element is laid out by the ordinary scrolling machinery, not as a fixed compositing layer. The same report is why `components.css` measures the full-height `body.stretch` layout as `min-height: 100dvh` on **`body`** and gives `html` no height at all: a document element exactly one viewport tall with content overflowing it is the other long-standing iOS trigger for anchoring a `bottom: 0` fixed element to the html box instead of the viewport. `mobile_tab_bar_css_test.exs` fails the build if either comes back.
- **The page paints edge to edge, so every edge is yours to keep clear** (issue
  #1464). `root.html.heex` declares `viewport-fit=cover` — which is the only
  reason `env(safe-area-inset-*)` reports anything but 0 — and links the web app
  manifest (`/site.webmanifest`, `VutuvWeb.PageController.webmanifest/2`, whose
  `scope: "/"` is what keeps an in-app link from opening in an overlay browser
  once the site is installed on a Home Screen). What that obliges: the phone tab
  bar grows by `env(safe-area-inset-bottom)` and pads the same amount away
  (`h-[calc(4rem+env(safe-area-inset-bottom))] pb-[env(safe-area-inset-bottom)]`,
  so its tabs keep their full 4rem above the home indicator) with
  `max(0.75rem, env(safe-area-inset-left|right))` at its sides; `<main>` and the
  footer reserve `calc(6rem + env(safe-area-inset-bottom))`; the full-screen chat
  subtracts the same from its `100dvh`; the lightbox's own controls carry their
  insets. **A container that holds the reading width takes `UI.gutter_class/0`**
  (`max(1rem, env(...))` per side) instead of `px-4` — the top bar's inner track,
  `<main>` and the footer's content column do. Every one of those `max()`es is
  exactly the old value where the device reports no inset, which is why none of
  it shows on a desktop; verify it on a real phone, not in a resized window.
  `mobile_tab_bar_css_test.exs` guards the bar and the reserved height.

- **The top bar is a three-track grid** (`grid-cols-[1fr_auto_1fr]`), not a flex row with an `ml-auto`: brand + nav on the left, the **site-wide people total** (`#people-total`) in the middle, the viewer's icons and avatar on the right. The equal `1fr` side tracks are what centre the middle cell **on the bar**, rather than on whatever space the flanking content happens to leave over — under auto margins the pill drifts with every change around it (logged out, admin pill, breakpoint), which is not "in the middle". Its slot (`#people-total-slot`) is always rendered, so the bar keeps its shape while the counter has nothing to show. **The bar is width-budgeted, and 768px is the tightest width** — the desktop nav appears at `md` but the viewport does not grow until `lg`, so an iPad in portrait carries the full four-label nav *and* the whole right-hand control row in 736 usable pixels. Measured there with the German labels and an admin signed in: left track 357 + right track 277 + this pill 91 + two gaps = 757, i.e. 21px over. Hence two things: the track gap steps `gap-4` → `lg:gap-6`, and the pill itself is `md:hidden lg:inline-flex` — shown on phones (nav hidden, ~72px to spare) and from `lg` (~219px to spare), hidden only in that one band, where it would push the bar into a horizontal scroll. **Re-measure at 768px before adding anything to this bar**, and measure it signed in as an admin (the "new members today" pill is part of the budget); a wide desktop window tells you nothing.
- **Active-nav highlight:** the shell marks the current page in both navs. It reads the request path (the `"path"` the layout already hands it via `shell_session/1` for badge-zeroing + `brand_path`), matches each nav destination with a route-boundary check (`ShellLive.on_route?/2` — `/messagesanna` is not "on" `/messages`, `/jobsy` not "on" `/jobs`; profile subpages like `/:slug/tags` do count as the member's Profile), and renders the matching item as the current location: `aria-current="page"` plus a distinct treatment (top bar → brand-tint pill `nav_link_class/1` with no hover; bottom tab → brand `text-brand-600 dark:text-brand-300` + `font-semibold`, both on the **link**, never on the label span — the press paint below has to have one element to work on). Like `brand_path`, it is the path **at mount**, which is exact for every nav destination (all reached by a full-reload `href`); it can go stale only after a cross-`live_session` `navigate`, the same accepted limitation `brand_path` has.
- **A nav press paints itself**, the same way a filter tab does and off the same rules in `app.css`. These links are plain `href`s on purpose (they cross `live_session`s), so a press is a whole new document: there is no socket round trip to hang feedback off and no ack to end it, and the pill would otherwise sit on the page being left until the next document paints. So `app.js` stamps `data-nav-pressing` on the pressed `[data-nav-item]` and on the document root, the pressed item takes its bar's current-page look, the item being left goes quiet, and `<main>` dims after `--press-pending-delay` (it is outside the shell LiveView, which is why the root carries the mark too). **The top bar's icon row is a `data-nav-bar` too** (Search, Bookmarks, Messages, Notifications): they are the same plain links to the same kind of whole new document, they inherit the nav palette, and a press fills the circle the way a hover already tints it. None of them is ever `aria-current`, so nothing quiets beside them; that is the whole difference. **The brand wordmark is deliberately left out**: there is no "current" state for it to take, and a tinted box tight around a logo reads as a rendering glitch rather than as feedback. Nothing has to take the paint off — the new document's own render does; a **bfcache** restore is the one case that does, and `pageshow` clears it. Three presses are deliberately not painted, because they leave this document as it is: a modified click (new tab), one something else already handled, and one on the page you are on. **The `dom.onBeforeElUpdated` hook on the LiveSocket is not optional**: both navs live inside `ShellLive`, so an unread badge ticking walks these nodes and morphdom drops every attribute the server did not render — without it the paint vanishes mid-load, rarely and unreproducibly. `press_paint_css_test.exs` guards that hook, the single shared paint rule, the one timing knob and the dark-mode palettes.
- **The phone tab bar's Feed tab has a second face: back to the top.** At the top of `/feed` it is the ordinary tab and a press reloads the page, which is what a reader who wants fresh posts reaches for. Half a screen down it wears an arrow instead and a press scrolls back up with no reload — the standing convention on phone tab bars, and the reason it changes its look first is that a control which behaves differently has to say so or the press reads as a reload. One attribute drives both halves and they cannot disagree: `scroll_top_tab.js` puts **`data-page-scrolled`** on `<html>` (not on the tab — ShellLive's next patch would drop it, the same reason the press paint above marks the root), and `components.css` reads it together with the server's **`data-scroll-top`**, which only ever sits on the tab whose own page is showing. Both glyphs ship in the markup; the arrow rests on an **inline `display: none`**, so a phone still running the previous release's stylesheet across a deploy draws one glyph instead of two. That is also why the reveal rule carries the file's one `!important`: an inline style yields to an important rule and to nothing else, and the tidier `hidden` attribute is unliftable here — preflight spells it `display: none !important` inside `@layer base`, and important declarations reverse the layer order with unlayered styles last. `mobile_tab_bar_css_test.exs` guards the pair.
- **Flash = top-right toasts** (`#toast-tray` in `app.html.heex`). Never add inline flash banners; `VutuvWeb.LayoutHTML.flash/1` and its empty partial were deleted along with the last inline calls. **Every** toast (info and error alike) auto-dismisses on one uniform timer — `TOAST_DISMISS_MS` in `app.js` (3s) — and the × closes it early; there is no per-toast auto-dismiss flag. Don't re-introduce a "sticky" toast variant.
- In-app real-time events go through `Vutuv.Activity` (PubSub on `"user:<id>"`) and `VutuvWeb.Presence`.
- **Language and viewer clock must be set per process.** `VutuvWeb.Plug.Locale`
  resolves all three per request — the Gettext locale, the date region and the

  `Live.InitAssigns` and `ShellLive.mount`). A new LiveView mounted outside the

  silently falls back to English and its stamps to the installation defaults.
- **Legacy page anatomy:** `.profile-header` h1 → `.breadcrumbs` → `.card-list` >
  `.card` — the header + breadcrumbs are emitted by `<.page_header title=… crumbs=… />`
  (new/edit pages pass only `crumbs`); the owner "Add" is the dashed `<.empty_add>`
  tile that `<.card_section add_href=…>` renders above the list (empty *or* populated),
  per-entry edit/delete is the calm `<.row_actions>` (placed in a `td.text-right` for

### CSS architecture (don't break it)

`app.css` order: `@import "tailwindcss"` → `@import "./components.css" layer(components)`,
**at the top** before `@source`/`@theme` — the `@import … layer()` only works there
(CSS ignores `@import` after other rules). `components.css` lives in the `components`
layer, so it beats Preflight (base) but loses to Tailwind utilities, which lets
hand-written pages use utilities freely. There is **no `legacy.css` anymore** — do not
reintroduce it (a regression test enforces this). Dev serves `/assets/app.css`
undigested, so hard-reload (Cmd+Shift+R) after a rebuild. **Dev does not use
`tailwind --watch`:** the v4 CLI's watch mode rebuilds from a cached copy of
`@import`ed CSS and ignores CSS edits outright (verified on 4.0.0 and 4.3.0), so
`VutuvWeb.TailwindWatcher` (wired as the dev watcher) runs a correct one-shot
build on every CSS/template/JS change instead. Edits to `components.css` reach
the browser within ~2s; if they ever don't, suspect that watcher first.

**A rule that has to beat a Tailwind utility cannot live in `components.css`** —
that layer loses to the utilities layer whatever its specificity, so the rule is
in the stylesheet, reads as if it applies, and quietly does nothing (only
DevTools striking the declaration through gives it away). Such a rule goes in
`app.css` **after** the `@theme` block, outside every layer, where it beats them
all. Keep those few and anchor every selector on a data attribute: the press
paint is the whole set today, shared by the /feed and /notifications filter
bars and by both navs, with its timing on `:root` as
`--press-pending-delay` and its four palettes named through `--press-on-bg` /
`--press-on-fg` / `--press-off-fg`.

**A new rule for an element `.markdown` also styles (`ol`, `li`, `a`, `td`, `p`)
needs a tag qualifier, or it has to sit after the `.markdown` block.** `.footnotes
ol` and `.markdown ol` are both (0,1,1), and the `.markdown` list rules live ~370
lines further down the file, so the later one wins every property they share.
Nothing fails and nothing warns: the rule is in the stylesheet and reads as if it
applies. The only tell is DevTools striking the declaration through, and you have
to go looking. That is how the footnote list shipped with the padding and margins
of an ordinary `<ol>` from issue #1147 until 2026-08-18, when it was finally
written as `div.footnotes ol`. Same trap, already recorded elsewhere in this file:
the Markdown table's last cell against `td:not(:first-child):last-child`, and the
upload drop zone against `.editform label`. When you add such a rule, check the
computed style in a browser rather than trusting that the selector is specific
enough to be about your thing.

**Text colour is never inherited onto a link or a button — every control on a
coloured surface names its own.** `components.css` sets `a, button { color:
var(--color-brand-600) }` for the classic pages, and *any* rule on the element
beats a colour the element merely **inherits** from an ancestor — specificity
never enters into it, so the utility layer winning over the components layer does
not help here. Put `text-white` on the coloured bar and the link inside it still
renders brand-600: that is how the acting-as banner shipped a brand-600 link and
button on a brand-700 bar, blue on blue and barely legible, while the sentence
beside them (a `<span>`, which no element rule names) was correctly white. So
when a surface sets a text colour for its contents, repeat that colour on every
`<a>` and `<button>` inside it; `<.button>` and the kit's other controls already
do. `acting_as_organization_test.exs` guards the banner's two.

- No em-dashes in UI copy (project-wide rule).
- **Everything must work on a phone, and too-small UX elements are a problem** (Stefan, 2026-07-26): every interactive control a member must hit on a phone gets a finger-sized target (aim ~40px; a compact variant is acceptable only where the space genuinely cannot fit it), inputs keep their full `input_class()` size (a shrunken input is a shrunken touch target), and a feature that only works with hover or drag needs a touch path — either a tap control (the reorder tool's arrow buttons) or a drag built on pointer events with a hold-to-lift so it works on touch too (the composer's PhotoStrip photo reorder is the model; native HTML5 drag alone never fires on touch). When in doubt, judge the mobile rendering first, not the desktop one.
